# Pointing Poker: decision log

Dated 10/15/2026. These decisions were made during planning and are closed. The build session
must not re-litigate them. Each entry is the choice, then the one-line reason.

Numbers are stable references; new decisions are appended, never renumbered.

## Product and scope

1. **Simplest possible architecture.** One app, no extra services; fewer moving parts for a small internal tool.
2. **One team per instance, one shared room.** Another team deploys its own service instance instead of us building rooms and tenancy.
3. **Jira write-back is in v1.** Saving Story Points to the ticket is the point of the tool, using the same credential as reads.
4. **No editing of the Jira ticket body (description or comments) from the app in v1.** An "Open in Jira" button covers it. Revisit later if needed.
5. **No database.** Game state lives in memory and the platform service runs one replica by default.
6. **No tests.** Verification is lint, type check, build, Docker smoke and manual browser checks.

## Identity and transport

7. **Identity comes from the auth proxy's headers** (names set per deployment in `IDENTITY_USER_ID_HEADER` and `IDENTITY_USERNAME_HEADER`), not API key forwarding. The headers are present on WebSocket upgrades too, and there is no user management to build.
8. **WebSockets with 25s pings.** The ALB in front has a 60s idle timeout, so idle tabs would drop without them.
9. **Dev-only `?devUser` override, double-gated.** It needs `NODE_ENV` not set to production and `ALLOW_DEV_USER=1`, and the proxy identity headers always win, so it cannot be reached in production.

## Stack

10. **Modern versions, verified against npm on 10/15/2026.** The user asked for the latest LTS and current tooling.
11. **Node 26 + Fastify 5.** Bun was rejected (ws shim and `node:http` upgrade bugs open as of 10/2026, exactly what `@fastify/websocket` sits on). Next.js was rejected (no native WebSocket server). Hono was rejected (its Node WebSocket path was unverified).
12. **Biome instead of ESLint.** `typescript-eslint` caps TypeScript at below 6.1, so ESLint with TS 7 is not possible today.
13. **Vite 8 + React 19 + MUI 9 via `@fastify/vite` in spa mode.** One process and one port for API, `/ws` and the client in dev and prod.
14. **mise for the toolchain.** It pins the tool versions so local and CI runs match.

## Tickets

15. **Queue scoped by project, optional board, and the needs-pointing label.** The team's main project has thousands of open unpointed tickets and no pointing label existed, so an unfiltered list is useless.
16. **Free-text search with per-user results.** Search is one person's lookup, so results go only to the requesting socket and are not room state.
17. **Full description and comments rendered from Jira HTML, sanitized on the server.** One place does the cleaning, and the client never trusts markup.

## UI and branding

18. **Layout C: queue, description, comments, and a one-row sticky bottom bar.** The team reads the ticket while voting, and the deck and actions stay reachable.
19. **Laptop widths only.** Internal tool on MacBook Pros inside the hosting platform's service report iframe; below `lg` things just stack.
20. **House style.** Navy #215470, Amber #F1A137 for Save only, Lato, light mode only.

## Process

21. **Buildspec security-review findings are inherited from the template and accepted.** They come from the template we copied, not from new code.
22. **`.env.example` is created by the user from `env-example.txt`.** Claude Code cannot write `.env*` files in this repo.
23. **Buildspecs removed; image pipeline to be decided before the first deploy (10/15/2026).** The user deleted `buildspec/`, and no registry or build pipeline is set up yet. CircleCI still runs lint, type check and build.
24. **Repo lives at `thatguyinabeanie/pointing-poker` (private), not an organization repo (10/15/2026).** The repo was created in the user's personal GitHub space.
25. **Image published to Docker Hub `gabemendoza1/pointing-poker` via repo scripts (10/15/2026).** `scripts/docker-build.sh` and `docker-push.sh` build linux/amd64 and tag by git SHA, with `latest` from clean main. CI did not push images at that point (see 27).
26. **CircleCI removed in favor of GitHub Actions (10/15/2026).** The repo lives on GitHub, so `.github/workflows/ci.yml` replaces `.circleci/config.yml` with the same gates.
27. **CI publishes to Docker Hub on main (10/15/2026).** The `publish` job pushes `:<short-sha>` and `:latest` as linux/amd64 after `checks` pass, using repo secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`.
28. **Docker Hub repo is public (10/15/2026).** The hosting platform cannot pull private images: its pre-deploy image check uses its own Docker Hub account, and it has no pull-secret support.
29. **Repo is now public, and pre-PR history was squashed (10/15/2026).** This supersedes the private visibility in decision 24. Before the first PR the history was squashed so no internal names remain in any commit.
30. **A ticket needs pointing if labeled or unpointed (10/15/2026).** The queue JQL is now `labels = X OR points is EMPTY`, and the "Labeled only" switch (still on by default, wire field `needsPointingOnly`) narrows it to labeled tickets so a pointed-but-labeled ticket can be re-pointed. This refines decision 15.
31. **Optional default board by name or id (10/15/2026).** `JIRA_DEFAULT_BOARD` takes a board name or numeric id and is resolved against the default project's boards at bootstrap, before the first queue fetch. A missing, unknown or ambiguous value falls back to no board, with one warn log.
32. **Queue mirrors the board's backlog page (10/15/2026).** With a board selected, the queue is read through the Agile API as sections: active sprints, then future sprints, then the backlog, each in rank order and capped at 50 tickets, with the board's own filter applied by Jira. The client shows the sections with collapsible headers; collapse state is per viewer (localStorage). Without a board the queue is one plain section. This replaces the single-JQL `filter = <id>` approach from decision 15 for boards.
33. **The "Labeled only" switch now defaults off (10/15/2026).** This is the user's decision and supersedes the default-on setting in decision 30. The `needs-pointing` label is not in use yet, so with the switch on the queue would start empty. The queue shows labeled or unpointed tickets by default, and board scoping plus sprint sections keep the list manageable.
34. **Label support removed; the queue is "not Done and unpointed" (10/15/2026).** This is the user's decision and supersedes the label parts of decisions 15, 30 and 33. The queue clause is only `statusCategory != Done AND <points field> is EMPTY`, so every unpointed ticket in a To Do status (Untriaged and Backlog alike) shows. The label paths were narrowing the queue: "Labeled only" hid unpointed Backlog tickets such as CIVIS-5661, which Jira confirms match the points rule. Removed: the "Labeled only" and "Clear label on save" switches, post-save label removal, and `JIRA_NEEDS_POINTING_LABEL`. The Story Points field-id logic (`cf[NNNNN]` or `"Story Points"`) is unchanged.
35. **Search text and the points pick survive a refresh, per tab (10/15/2026).** This is the user's decision. Room state already lives on the server; these two were plain React state and were lost on refresh. Both go to `sessionStorage` (`pp.search.query`, `pp.points.pick`), not `localStorage`, so two open tabs never overwrite each other. The points pick is tagged with the ticket key and round and is used only when both match during a reveal, so a new reveal or ticket never keeps a stale pick. Collapsed queue sections stay in `localStorage` (decision 32). No server or protocol change.
36. **Keep the production startup warning for missing identity header names (10/15/2026).** This is the user's decision. In production, when `IDENTITY_USER_ID_HEADER` and `IDENTITY_USERNAME_HEADER` are not both set, `index.ts` logs one warning at startup (`identityConfigWarning()` in `server/identity.ts`) naming the variables only, never values. Why: a deploy missing the header names otherwise rejects every user with 4401 and the logs give no hint. Dev and local runs never warn.
37. **Every branch push publishes an image; `:latest` stays main-only (10/15/2026).** This is the user's decision and refines decision 27. The `publish` job now runs on any branch push (not pull requests, not tags) and tags `:<short-sha>`, `:<branch>` (sanitized, `build/v1` becomes `build-v1`) and `:<branch>-<run-number>` (for example `build-v1-57`; the run number is GitHub's per-workflow run counter, and a re-run keeps the same number), so a branch can be tried on the hosting platform before it merges. `:latest` is enabled only on the default branch, because it is what the platform deploys and a branch must never overwrite it.
38. **UI redesign: slim header, two-column layout, two-line queue rows, ticket tabs, card-style players (10/16/2026).** This is the user's decision. Inside the published report the app's navy `AppBar` sat under the platform nav and wasted vertical space, and the panes and bottom bar used room poorly. The header is now one slim light row (queue controls left, title centered, status dot and username right), `Layout` has two columns at `lg+` (queue and main) with comments moved into a Description and Comments tab view, queue rows are two lines and clickable, the bottom bar is a `1fr auto 1fr` grid, and players render as avatars holding cards with outliers marked after reveal. Client only: no protocol, server or `shared/` change, and behavior of the queue, voting and saving is unchanged. Full design: [`docs/superpowers/specs/2026-10-16-ui-redesign-design.md`](../superpowers/specs/2026-10-16-ui-redesign-design.md). `03-client.md` describes the new components; the files under `reference/` and the mock are the earlier design and are not kept in sync.

39. **The queue pane is resizable, and the width is remembered per viewer (10/16/2026).** This is the user's decision and extends decision 38. The fixed one-third queue column was too narrow for long ticket titles for some viewers and too wide for others. At `lg+` a divider with a grip now sits between the panes: drag it, use the arrow keys, or double-click to reset. The width is clamped to 260px through half the row and stored in px in `localStorage` (`pp.layout.queueWidth`), so it is a per-browser convenience and never reaches the server. Below `lg` the layout still stacks with no handle. Client only. Described in `03-client.md` under Layout.

40. **Session history and ticket history (10/20/2026).** This is the user's decision. The room had no record of what it already pointed, so a ticket could be pointed twice without anyone noticing, and a ticket's Jira changes (status moves, earlier point changes, who changed what) meant leaving the app. The left pane now has Queue and History tabs. Session history lists the tickets revealed in this room, newest first, with average, range or consensus, "re-voted", "✓ saved" and the saved points; a row picks the ticket again. The ticket view gets a History tab with the Jira changelog. Session history is in server memory only (`GameState.history`, shipped in every snapshot), so a restart clears it, and it is capped at 50 rows with one row per ticket key. Ticket history is read from Jira when the ticket loads and is not stored, capped at the newest 100 entries with values over 200 characters, and the Description and Environment fields shown as "edited" without their text. A failed or short changelog read shows no history rather than a partial one. No new client commands and no storage on the server. The selected left tab is per browser tab (`sessionStorage`, `pp.left.tab`). Full design: [`docs/superpowers/specs/2026-10-20-history-design.md`](../superpowers/specs/2026-10-20-history-design.md). Described in `02-server.md` (game state, save callback, "Ticket history") and `03-client.md` (`LeftPanel`, `SessionHistory`, `TicketRowFrame`, `TicketHistory`).

41. **Cards auto-reveal once every connected player has voted (11/04/2026).** This is the user's decision. Waiting for someone to press Reveal after the last vote added a step to every round. A shared "Auto-reveal" switch, on by default, now flips the cards the moment every connected player holds a card. Only connected players count, so a closed tab never stalls the room, and their votes still show on reveal. The flip is instant, with no countdown or timer. It triggers on a vote, on the last non-voter disconnecting, and on turning the switch on when everyone connected has already voted. It records session history like a manual reveal. The Reveal button stays for partial reveals. The switch is room state (`GameState.autoReveal`, `Snapshot.autoReveal`, command `setAutoReveal`) and survives new rounds; only a server restart resets it to on. The switch lives in the header next to Project and Board because in the action bar it wrapped the bottom bar after reveal. Described in `02-server.md` and `03-client.md`.

42. **A 0.5 card in the deck (11/04/2026).** This is the user's decision. Small tickets had no value between 0 and 1, so the room rounded them up or down. The deck now has a `0.5` card between `0` and `1`. It is a numeric card: it counts toward average, min, max and consensus, and it can be saved to Jira as Story Points 0.5. `isNumericCard` accepts one decimal part, and the `saveEstimate` schema no longer requires an integer; `canSave` still allows only numeric deck values. Described in `01-overview.md` and `02-server.md`.

43. **Save feedback is a top-center toast, shared with errors (11/04/2026).** This is the user's decision. The inline alert after Save to Jira ("Saved 2 pts by name" or Jira's error) made the bottom bar taller, so the whole layout jumped. The result now shows as a toast at the top center, for everyone in the room, and only for a client that sees the save go from `saving` to `saved` or `error`, so joining or refreshing afterwards shows nothing. Errors and save results share one `NoticeSnackbar` (severity error or success, 6 seconds, close button, ignores clickaway), so two toasts never stack, and the existing error toasts moved to top center too. The Save button spinner is unchanged. Client only: no server or protocol change. Described in `03-client.md`.

44. **Each queue row shows its epic as a chip in Jira's color (11/04/2026).** This is the user's decision. The team asked to see which epic a ticket belongs to without opening it. Line 1 of each queue and search row now carries an outlined chip between the key and the status badge, with a dot in the epic's Jira color and the epic name. Matching Jira's colors costs one extra request per refresh, because the epic color is not on the child ticket. An epic Jira gives no color shows a gray dot. The chip is on line 1 so line 2 stays the summary, and it truncates before the key or badge do. Session history rows are unchanged. Described in `03-client.md`.

45. **Votes can change after the reveal (11/05/2026).** This is the user's decision. Once the cards flipped, a split room could only move on: nobody could change a vote after the discussion, so the average and the suggested points stayed at the split. `vote` now works in `voting` and `revealed` (idle still returns `not_voting`), and the toggle still applies: voting the same card again withdraws it. A change refreshes the ticket's session history row in place (`refreshRevealedRow`: average, range, consensus and voters) without setting `revoted`, because it is the same reveal and not a new round; the row keeps its position and `savedPoints`. A change that leaves zero votes keeps the row as it was. A vote after an empty reveal (zero votes when the cards flipped) is the exception: the empty reveal recorded nothing, so the vote goes through `recordReveal` and creates the row, or marks an older row re-voted, as a fresh reveal would; otherwise it would never reach History (found in the final review, 11/05/2026). Auto-reveal is unaffected, since it only acts while voting. The "Points" select follows the most common vote when the votes move, unless someone picked a value by hand for this ticket and round. Described in `02-server.md` and `03-client.md`.

46. **Auto-advance after a save (11/05/2026).** This is the user's decision. After Save to Jira someone still had to pick the next ticket by hand, which added a step to every round. A shared "Auto-advance" switch in the header, off by default, now loads the next ticket once a save succeeds. It is off by default because it moves the whole room to another ticket, which is surprising for a room that did not ask for it. The switch is room state (`GameState.autoAdvance`, `Snapshot.autoAdvance`, command `setAutoAdvance`) and survives new rounds; only a server restart turns it off. The next ticket is the one after the saved ticket in queue order (sprints first, then backlog), or the first queue ticket when the saved one is not queued (`nextQueueKey`). It is taken before the Jira write, because the refetch drops the saved ticket from the queue. It does not advance when the save fails, when the switch is off, when the queue has nothing after the saved ticket, when a reset or ticket load changed the round during the save or the refetch, or when a ticket load is still waiting on Jira (a room-level `loadsPending` counter, because a load in flight has not changed the round yet and the later advance would otherwise win), or when a newer save was accepted after it (a room-level `saveAttempt` counter). The last rule came from the PR review on 11/05/2026: the write lock is released before the queue refetch, so a second Save can start during it, and if the older save advanced then, the newer write would land on a changed round and a failure of it would be dropped as stale and never shown. A newer save cancels the older save's advance whether it is still pending or already failed. A vote cast on the revealed round just as the room advances lands on the new ticket and can be withdrawn. A load error reaches the socket that saved. Described in `02-server.md` and `03-client.md`.

47. **Median in the reveal stats (11/05/2026).** This is the user's decision. The reveal showed the average and range, but a single high or low card pulled the average, and the median is the number the room is usually asking about. `summarize` now returns `median` in `Snapshot.stats`, computed over numeric votes only, so non-numeric cards (`?`, `☕`) are ignored the same way they are for the average. With an odd count it is the middle vote; with an even count it is the mean of the two middle votes, rounded to one decimal like the average, so `3` and `5` give `4` and `0.5`, `1`, `2` give `1`. It is null when no numeric vote exists. Median is not stored on session history rows: `recordReveal` and `refreshRevealedRow` copy stats field by field, and the history row keeps average, min, max, consensus and voters only. Described in `02-server.md`.

48. **Two-tier bottom bar (11/05/2026).** This is the user's decision. At a 1440px laptop width the 11-card deck took the middle of the one-row bar and left each side about 350px. After a reveal both sides overflowed: the stats chips wrapped beside the players, and the points select, Save to Jira and Next ticket wrapped beside the deck. The bar then grew to its 140px cap and scrolled, so the panes above jumped. The user compared three full-page mockups (a players strip above the ticket, a players rail beside it, and a two-tier bar) and chose the two-tier bar, which keeps everything at the bottom. The bar now has a players row above the deck row. The players row uses the deck row's `1fr auto 1fr` grid, so the player pills (avatar, name, mini card) sit centered over the deck; the user asked for the centering on the same day, after first seeing the pills left-aligned. Its right cell is `RoundSummary`: "N of M voted" while voting, and after the reveal a small bar chart of the votes in deck order, "Avg · Median" and one chip (Consensus, Spread min–max, or No numeric votes). It replaces the per-card count chips. When the pills do not fit, every pill drops its name together (compact mode). The fit is measured on a hidden copy that always shows the names, against the row width minus the summary's width on both sides, so dropping names cannot flip the decision back and the pills stay centered on the deck. The summary counts as at least `SUMMARY_RESERVED_WIDTH` (400px, a typical revealed summary rounded up), so compact mode does not depend on the phase: the user saw 7 players at 1440px show names while voting and drop them at the reveal, and chose on 11/05/2026 that a team that fits keeps its names in both phases and a team that does not is compact in both. The hidden copy is clipped by an absolutely positioned box so it never widens the page. The bar is a fixed 148px at `lg` in every phase (`BOTTOM_BAR_HEIGHT`), so the panes never jump; the earlier 88px minimum and 140px cap are gone. The revealed actions are shorter so they fit one row: the select is labeled "Points" and is 96px wide, "Save to Jira" is now "Save" (its `aria-label` stays "Save to Jira" and it is still the only amber control), and "Next ticket" is now "Next". At `lg` the action row never wraps; between `lg` and `xl` the deck, its row gap and the action buttons are slightly tighter so the row fits beside the deck at a 1200px layout, with the Save spinner (the final review found "Next" overflowing the bar there). Described in `03-client.md`.

49. **Epic chips are tinted with the epic color (11/05/2026).** This is the user's decision. The epic chip on queue and search rows was an outlined element on the white row, and its outline blended into the row, so the chip did not separate from it. The user picked a tint of the epic's own color over a neutral gray. The chip fill is the epic color at 12% and its outline is the epic color at 50%, both computed from `epicHex(epic.color)`. An epic with no Jira color uses the gray from `NO_COLOR_HEX`, with no special case. The outline stays an inset shadow so the row height does not change. It applies wherever `TicketRowFrame` shows an epic, which is the queue and search rows; session history rows show no epic. Described in `03-client.md`.

50. **Ticket type filter (11/05/2026).** This is the user's decision. The team wanted to narrow the queue by ticket type, for example to point only Stories and Bugs. The user chose a shared room filter applied in the Jira query over a per-viewer filter in the browser. Because it is part of the JQL (`AND issuetype in (...)` on the needs-pointing clause), the per-section cap of 50 and the counts apply after filtering, so a filtered queue is complete rather than a filtered slice of the first 50 tickets. It is room state like Project and Board (`QueueSettings.issueTypes`), so everyone sees the same queue. An empty list means all types. The menu lists the project's types from `GET /rest/api/3/project/{key}` (`Snapshot.issueTypes`), and the server keeps only names from that list, because Jira answers 400 to an unknown type name. Changing the project clears the filter, because each project has its own types. If the type list cannot be loaded, the menu stays disabled and the queue is unfiltered, with one warn log and no error to the user. Free-text search is not filtered: it is one person's lookup and must still find any ticket. The Auto-reveal and Auto-advance switches moved to the right side of the header, before the status dot, so the left side holds only Project, Board, Type and Refresh. One header row then needs about 1060px, so below `lg` the header wraps to two rows (controls, then switches and status); the final review ruled `md`, but one row cannot fit at 1024px. The Type menu sends its selection once, when it closes, so clicks are never lost and the queue refetches once per menu session. Described in `02-server.md` and `03-client.md`.
