# Pointing Poker: client (frontend) specification

This document is self-contained. A coding session implementing the `client/` folder of the `pointing-poker` repo should need nothing else. Where it says "reference implementation", it means files that were already written and reviewed and are copied into the repo at `docs/spec/reference/client/src/components/*.tsx` and `docs/spec/reference/client/src/lib/estimate.ts`. Copy them into `client/src/` unchanged unless this document says otherwise. The shared contract lives in `shared/protocol.ts` and `shared/deck.ts` (already written; do not edit them). `Ticket` in `protocol.ts` carries `descriptionHtml`, `comments` (`TicketComment[]`, oldest first), `assignee`, `priority` and `labels` in addition to the summary fields. `shared/constants.ts` also exists and exports `ISSUE_KEY` and `MIN_QUERY_LENGTH`. The reference `QueuePanel.tsx` still has the label switches; the repo version drops them (decision 34).

> **Redesign (10/16/2026).** The header, layout, queue rows, ticket view, bottom bar and players were redesigned. The design is `docs/superpowers/specs/2026-10-16-ui-redesign-design.md` (decision 38). Where this file describes the earlier `TopBar`, three-pane layout, `TicketDescription`, `TicketComments` pane or `ParticipantChips`, the sections below now describe the redesigned components instead. The files under `docs/spec/reference/client/` and the mock are the earlier design and are not kept in sync.
>
> **Hand of cards (11/05/2026).** The bottom bar was then replaced by a players strip at the top of the Ticket pane, a floating hand of cards and a floating results pill (decision 51, design `docs/superpowers/specs/2026-11-05-hand-of-cards-design.md`). `Deck.tsx`, `ActionBar.tsx` and `RoundSummary.tsx` were deleted; where the sections below mention the bottom bar, they describe the strip, `Hand` and `ResultsPill` instead.
>
> **Results in the strip (11/06/2026).** The user then moved the results out of the floating pill and into the players strip, next to the names and their cards (decision 51, dated note). `ResultsPill.tsx` became `RoundResults.tsx`, rendered by `RoundControls`; the floating group is only the hand in every phase.

## 1. Scope

The client is one page with no router. It uses the stock MUI 9 theme with only the font family changed to Lato (Roboto fallback). It uses the whole page width: two columns (queue on the left, ticket view on the right) under a slim header, with the players strip at the top of the ticket pane and the vote cards and results floating at the bottom edge of the window, over the panes. There is no bottom bar. The target is laptop widths (internal tool, MacBook Pro screens, inside the hosting platform's service report iframe), so the full layout applies from the `lg` breakpoint (1200px) up. There is no phone layout work. Below `lg` the panes simply stack at full width and nothing should break; that is the whole requirement there. Everything is one shared room: there is no room picker or login screen. The only settings are the shared ticket queue settings (section 2, QueuePanel), which are room state, not per-user preferences. Identity comes from the server (auth proxy headers), so the client never asks who the user is. There are no client tests in v1 (decision, see `08-decision-log.md`). Do not add any dependency beyond what `package.json` already lists: react, react-dom, @mui/material, @mui/icons-material, @emotion/react, @emotion/styled. Do not add a router, state library, or form library.

Lint is Biome (`npm run lint` is `biome ci .`): double quotes, 2-space indent, line width 100, React lint domain on. Type check is `tsc --noEmit -p tsconfig.json` (strict, `verbatimModuleSyntax`, `allowImportingTsExtensions`). That means: always `import type` for type-only imports, and always write the `.ts`/`.tsx` extension on relative imports, as the reference files do.

### lib/estimate.ts

`suggestPoints(stats: Snapshot["stats"], deck: readonly string[]): string | null`. Returns null when `stats` is null. Otherwise it scans `stats.counts` and picks the numeric card with the highest count. A card is eligible only if `isNumericCard(card)`, `deck.includes(card)` and `count > 0`. So `?` and the coffee card are never suggested, and counts for cards that are not in the deck passed in are ignored. On a tie the numerically higher card wins ("when the room is split, the cautious estimate is the bigger one"). Returns null when no eligible card exists. Returns a string (a card), not a number.

### components/Header.tsx

Props: `{ connected: boolean; meName?: string; controls?: ReactNode; actions?: ReactNode }`. A `Box component="header"` of height `HEADER_HEIGHT` at `lg` (48, from `layoutConstants.ts`, so `Layout` and `Header` always agree), light grey background and a bottom border, not an `AppBar`. From `lg` up it is one fixed 48px row, a three-column grid `1fr auto 1fr` that keeps the title centered whatever the side widths are. Left: the `controls` slot (App passes `QueueControls`, and passes nothing until the first snapshot). Center: "Pointing Poker" as the page's only `h1`. It is always rendered; below `lg`, where the two rows leave no centered slot, it is visually hidden with the clip pattern (absolute, 1px by 1px, `overflow: hidden`, `clip: rect(0 0 0 0)`, `whiteSpace: nowrap`, margin -1px, no border or padding) rather than `display: none`, so screen readers still find a page heading at every width. Right: the actions and status. One row needs about 1060px: the controls take 484px (three 140px selects, Refresh and the gaps), the title 132px and the right side about 380px, plus the 16px padding on each side and two 16px gaps. Below `lg` the header is therefore one column with two rows (`height: auto`, `minHeight` 48, `py` 8px): row 1 is the controls, row 2 the actions and status, aligned right. Both rows may wrap at phone width (the controls need 394px at `xs`). Measured with no overlap at 320, 768, 1024, 1199, 1200 and 1440px wide. `Layout` uses `HEADER_HEIGHT` only at `lg` and up, so the taller header below `lg` needs nothing else. (The final review on 11/05/2026 ruled two rows below `md`; measuring showed one row cannot fit at 1024px, so the breakpoint is `lg`.) Right side: the `actions` slot first (App passes the Auto-reveal and Auto-advance switches once a snapshot exists), in its own flex row with gap 1 (`flexShrink: 0` at `lg`, wrapping below it), then a status dot (green with tooltip "Connected", amber with tooltip and visible text "Reconnecting…" when disconnected) and the viewer's username. Color is never the only signal.

### components/QueueControls.tsx

Props: `{ settings, projects, boards, issueTypes, epics, disabled, onChangeSettings, onRefresh, refreshing? }`. The Project select, Board select and Refresh icon button that used to be the first row of `QueuePanel`, with the same handlers and disabled rules, a Type select (decision 50) and an Epic select (decision 52) between Board and Refresh. Type is a `Select multiple` labeled "Type" (`minWidth` 110 at `xs` and 140 from `sm`, like Project and Board; `maxWidth` 220, 130 from `lg` to `xl`, 220 again from `xl`, also like Project, Board and Epic) over `issueTypes` (App passes `snapshot.issueTypes`, the project's type names). Closed, its value is `settings.issueTypes`, the room's selection, shown as is so the closed select matches what the server filters by. Its `open` state is controlled (`open`, `onOpen`, `onClose`). The draft logic lives in `useRoomMultiSelect` (below), which Type and Epic share. Opening copies `settings.issueTypes` into a local `draft` and remembers it, with `settings.projectKey`, as the value at open; while open the value and the checkboxes show the draft. A change only updates the draft. Closing calls `onChangeSettings({ issueTypes: draft })` once, and only when the draft differs from the value at open as a set and the room's current `settings.issueTypes` still equals the value at open (`sameNames` from `shared/constants.ts`, the same check the server uses). Two refs hold the selection this client last sent (`lastSent`) and the room's selection when it sent (`sentFrom`); both are cleared whenever the room's selection changes after a send, whatever the server answered (the echo, a selection with dropped type names, or another user's edit). Opening uses `lastSent` as the value at open, and closing accepts the room matching the value at open, `lastSent` or `sentFrom` as unchanged. So a quick close and reopen before the echo does not drop the second edit, and a send the server altered or rejected does not leave the menu dropping every later edit (PR follow-up, 11/05/2026). Otherwise the draft is dropped silently: someone else changed the filter while the menu was open, and the draft, built on the old selection, would undo their change. When `settings.projectKey` changes or the select becomes disabled while the menu is open, the menu closes and the draft is discarded without sending (PR follow-up, 11/05/2026). Sending on every click made each click a room-wide queue refetch, and a click that landed before the previous snapshot came back was computed from the stale selection and undid the earlier click; with the draft no click is lost and the room refetches once per menu session. It uses `displayEmpty` (MUI then notches the outline) with a shrunk `InputLabel`, so the label never sits on the text. `renderValue` shows "All types" for an empty selection, the name for one type, and a count for two or more ("2 types"), because the joined names were the widest value in the header. The full list stays in the menu and in the select's `title` attribute ("All types" or the names joined with ", "). Each `MenuItem` (dense) holds a small `Checkbox` and a `ListItemText` with the name. A string value from autofill is split on commas. It is disabled when `disabled` is true or when `issueTypes` is empty (no project, or the type list failed to load).

`useRoomMultiSelect({ roomValue, resetKey, disabled, onSend })` (`client/src/useRoomMultiSelect.ts`, next to `useGameSocket.ts`) holds that draft logic once: the session captured at open, the `lastSent` and `sentFrom` refs and the effect that clears them when the room's value changes, one send on close, dropping the draft when the room changed meanwhile, and closing when `resetKey` (the project key) changes or `disabled` turns true. It returns `{ value, open, onOpen, onChange, onClose }`: `value` is the draft while open and `roomValue` while closed, and `onChange` takes the Select's change event (it also splits an autofill string on commas). Type calls it with `roomValue: settings.issueTypes` and `onSend: (issueTypes) => onChangeSettings({ issueTypes })`; Epic with `settings.epicKeys` and `epicKeys`.

The Epic select follows Type after it: `Select multiple` labeled "Epic", `displayEmpty` with a shrunk label, the same widths, over `epics` (App passes `snapshot.epics`: the epics of the tickets that need points first, then the project's other open epics, each in rank order). Closed, it shows the room's `settings.epicKeys` as is: "All epics" for none, the epic's name for one, "2 epics" for two or more, on one line that truncates with an ellipsis. Its `title` holds the full names joined with ", ". A key that is not in `epics` (an epic closed since it was selected) shows as the key itself. Each dense `MenuItem` holds a small `Checkbox`, a 10px round dot in `epicHex(epic.color)`, and a `ListItemText` with the name and the key as secondary text. The menu can list every open epic, so its paper has a `maxHeight` of 360px and scrolls. At the top of the menu is a search field (`TextField` size small, placeholder "Search epics", `aria-label` "Search epics") inside a sticky `ListSubheader`, so it stays pinned while the rows scroll under it (opaque `background.paper`). It filters by name or key, case-insensitive; the text is local to the client and is cleared when the menu closes. Below it come two non-sticky `ListSubheader` groups, "In the queue" (`inQueue`) and "Other open epics", and a group with no rows is hidden. Selected epics are always listed, in their group, even when the text does not match them, so a checked row is never hidden. When no epic matches, a header-style line says "No epics match". The search field and the headers have no `value`, so Select does not treat them as options, and `useRoomMultiSelect`'s `onChange` ignores any `undefined` entry in the list. The menu has `autoFocus: false` so the first row does not take focus, and the field is focused when the menu opens (`autoFocus`, plus a focus in the transition's `onEntered`). Keys typed in the field stop at the field, except Escape (closes the menu, which sends the selection once) and Tab (the menu closes on it), so Select's and the menu's type-ahead never see them. Arrow Down in the field moves focus to the first epic row by hand, since the menu's arrow navigation does not see the field; from there the arrow keys, Space and Enter work as in any Select. It is disabled when `disabled` is true or `epics` is empty (no project, the project has no open epic and no queued ticket has one, or the epic list failed to load). A project with no "Epic" issue type is no longer a special case. One row with no wrap from `lg`, where the header is a fixed 48px; below `lg` the header grows, so the `Stack` (`useFlexGap`) wraps with a 16px row gap that leaves room for the floating labels (see Header). The Project and Board selects have `minWidth` 110 at `xs` and 140 from `sm`. All four selects share one `sx` with `maxWidth` 220 below `lg`, 130 from `lg` and 220 from `xl` (it was 160 with three selects; 130 was chosen to fit four in one row and is checked in the browser), and a longer value is truncated with an ellipsis by the select's own nowrap styles; each select's `title` attribute holds the full Project ("KEY (Name)") or Board name. At `lg` the header's left column is about 500px at a 1200px layout, so 220px selects with long names ran toward the centered title. Measured in Chrome (11/05/2026) with the longest real names (project "OKR2 (Civis Platform Usage and Adoption Metrics)", board "Civis Platform Usage and Adoption Metrics") and three types: the controls' right edge stays left of the title's left edge by 16px at 1200, 34px at 1280 and 77px at 1366. `refreshing` (App passes `snapshot.queue.loading`) keeps Refresh disabled while the queue loads. The Auto-reveal switch is not part of this component, which stays about the queue. App passes it to the Header's `actions` slot, on the right before the status dot (moved from the left group by decision 50, so the left holds only Project, Board, Type, Epic and Refresh): a `RoomSwitch` (`client/src/components/RoomSwitch.tsx`, props `{ label, checked, disabled, onToggle(enabled) }`): a `FormControlLabel` (`sx` `ml: 0`, `mr: 0`, `flexShrink: 0`, `whiteSpace: "nowrap"`) around a `Switch size="small"`, vertically centered by the slot's flex `alignItems: "center"`. It keeps no local state. The first is labeled "Auto-reveal": `checked` is `snapshot.autoReveal`, `disabled` follows `disabled`, and `onToggle` sends `{ type: "setAutoReveal", enabled }`. It is shared room state, on by default (decision 41), so every viewer sees the same value. The second is labeled "Auto-advance": `checked` is `snapshot.autoAdvance`, and `onToggle` sends `{ type: "setAutoAdvance", enabled }`. It is shared room state, off by default (decision 46).

### components/LeftPanel.tsx

Props: the `QueuePanel` props plus `history: SessionHistoryEntry[]` (App passes `snapshot.history`). It owns the left pane's `Paper` and its two tabs, "Queue" and "History"; `QueuePanel` no longer draws an outer `Paper`. The History tab label carries a count badge (`history.length`, shown at zero). The tab bar is sticky at the top of the pane, because `Layout`'s pane is the element that scrolls. The selected tab is per tab of the browser: `sessionStorage` key `pp.left.tab` (`"queue"` or `"history"`, anything else reads as `"queue"`) through `readJson` and `writeJson`. Both panels stay mounted and the inactive one is hidden (`hidden`), because remounting `QueuePanel` would re-send its restored search query to Jira on every tab switch. `SessionHistory` gets `history`, `currentKey`, `disabled` and `onPick` from the same props.

### components/SessionHistory.tsx

Props: `{ history: SessionHistoryEntry[]; currentKey: string | null; disabled: boolean; onPick: (key: string) => void }`. With no rows it shows the muted text "Nothing pointed yet in this room." Otherwise a dense `List` with one `TicketRowFrame` per row, in array order (the server sends newest first). The badge is the saved points, or "–" when the ticket was revealed but not saved. The second line is a detail line, also set as its `title` tooltip: `avg {average}`, then "consensus" or `{min}–{max}`, then "re-voted" when `revoted`, then "✓ saved" when `savedPoints` is set, then `relativeTime(revealedAt)`, joined with " · ". When `average` is null (only non-numeric votes) the avg and range parts are left out. Clicking a row calls `onPick(key)`, which loads that ticket again for the room, exactly like a queue row, and the current ticket's row is highlighted and not clickable. The history is room state and lasts until a server restart; it is not stored in the browser.

### components/TicketRowFrame.tsx

Props: `{ issueType; ticketKey; url; isCurrent; disabled; onPick; badge: ReactNode; epic?: QueueEpic | null; secondLine: ReactNode }`. The row layout that used to live inside `QueuePanel`'s `TicketRows`, extracted so the queue, the search results and `SessionHistory` look and behave the same: type icon, key as a `Link` to `url` (new tab, `rel="noopener noreferrer"`, its click does not pick the ticket), an epic chip when `epic` is set (a rounded element with a 12% fill and a 50% inset outline of `epicHex(epic.color)`, so it stands off the white row; the outline is an inset shadow so the row height does not change; an 8px dot in the same color and the epic name in caption text; the name truncates with an ellipsis and has the full name as its `title`, so the key and the badge always stay visible; no click handler of its own), a badge on the right, then the second line on one line with ellipsis. The root is a `ListItem` (`li`, `disablePadding`) holding the `ListItemButton`, so rows are list items of the `List` that both callers render them in (assistive technology announces them with their position). The whole row is the `ListItemButton`; the current row is highlighted with a left accent border, has `aria-current`, and ignores clicks. Other rows are disabled while `disabled` is true. `QueuePanel` passes the status as the badge, `item.epic` as the epic and the summary as the second line. `SessionHistory` passes no epic.

### components/QueuePanel.tsx

Props: `{ queue: QueueState; searchResults: SearchResults | null; currentKey: string | null; disabled: boolean; onPick: (key: string) => void; onSearch: (query: string) => void; boardUrl: string | null }`. The settings row (Project, Board, Refresh) moved to `QueueControls` in the header, so the rows below that mention it no longer apply to this component. `boardUrl` is computed in `App.tsx` (memoized; the Jira origin comes from the first item's `url`, and the URL needs a project key and a board id) and is the target of the "Open the full board in Jira" link. Rows are two lines (type icon, key link and status badge; then the summary with ellipsis) and the whole row is a button that calls `onPick`; the current ticket's row is highlighted and not clickable (design spec section 3). `SearchResults` is `{ query: string; items: QueueItem[]; error: string | null; pending: boolean }`, exported from `QueuePanel.tsx` and structurally identical to the hook's `searchResults` value. Types come from `shared/protocol.ts`. The team picks the next ticket from a shared queue of unpointed Jira tickets instead of typing a key. Settings are shared room state: changing one changes the queue for everyone.

MUI: `Stack spacing={2}` (the `Paper` and the padding now come from `LeftPanel`) with these rows, top to bottom:

1. Settings: not part of this component. The Project and Board selects and Refresh live in `QueueControls` in the header. The component starts with the search box.
2. Search: a `TextField size="small"` labeled "Search tickets (key or text)" with a `SearchIcon` start adornment. Local state holds the text; every change calls `onSearch(text)` (the hook debounces and ignores short queries). The text is persisted per tab in `sessionStorage` key `pp.search.query` (a JSON string; removed when the box is cleared) and restored on load. A search sent while the socket is down is dropped, so an effect keyed on `disabled` re-sends a non-empty query each time the connection comes up, which brings restored results back after a refresh and refreshes them after a reconnect. Below it, driven by `searchResults`: a `LinearProgress aria-label="Searching"` while `pending`; an inline `Alert severity="warning"` with `error` when not pending and `error` is set; "No matches" when not pending and `items` is empty; otherwise the result rows. When `searchResults` is null nothing renders.
3. Queue status: a `LinearProgress aria-label="Loading queue"` while `queue.loading`; else an inline `Alert severity="warning"` with `queue.error`; else a `Typography variant="caption"` "{n} tickets · updated {time}" (n is the sum of the sections' `total`; time from `fetchedAt` via `toLocaleTimeString`, omitted when null).
4. Queue list: unless loading or error, and when `queue.sections` is empty, the text "No unpointed tickets. Change the project or board, or refresh." Otherwise one block per section, in order. Kind `all` (no board) has no header and is a plain `TicketRows` list. Other kinds (`active`, `future`, `backlog`) get a dense header row: a button with `aria-expanded` and `aria-controls`, an ExpandMore or ExpandLess icon, the section name, a small "active" or "future" label (none for backlog), and the count (`total` when `items.length === total`, else "{items.length} of {total}"). The body is an MUI `Collapse`. When `items.length < total`, the last row is the link "Open the full board in Jira" to `{jiraBase}/jira/software/c/projects/{projectKey}/boards/{boardId}/backlog`, shown only when the Jira base URL can be derived from the first item's `url` origin, otherwise omitted. Collapse state is per viewer: React state, default all expanded, persisted to `localStorage` key `pp.queue.collapsed` (a JSON array of section ids). All Web Storage access goes through `client/src/storage.ts` (`readJson`, `writeJson`, `removeItem`), which wraps every call in try/catch and ignores failures. The queue list stays separate from, and below, the search results.
Rows (queue and search results share one internal `TicketRows` component): two lines per row. Line 1 is the issue-type icon (a small map from Jira type name to an MUI icon, generic for others), the key as a `Link` to `item.url` (`rel="noopener noreferrer"`, opens in a new tab, and its click does not point the ticket), an epic chip when the item has an epic (colored dot and the epic name, falling back to the epic key when the name is empty; see `TicketRowFrame`), and the status as a small badge on the right. The issue-type icons are colored per type. Line 2 is the summary on one line with ellipsis and the full text in a `title` tooltip. The whole row is a button that calls `onPick(item.key)`; the row whose key equals `currentKey` is highlighted (tint and left accent border) and not clickable.

### components/Layout.tsx

Props: `{ left: ReactNode; main: ReactNode; floating: ReactNode }`. It holds one piece of state, the tickets pane width, and no data. It renders a `Container maxWidth={false}` with `sx={{ px: { xs: 2, lg: 3 } }}` (full width), then a flex row of the two panes, then the fade band and the floating group. There is no bottom bar: `BOTTOM_BAR_HEIGHT`, `BAR_GAP` and the `--bottom-bar-height` variable are gone (decision 51).

| Slot | Position | Content from App |
|---|---|---|
| `left` | left pane, fixed px width at `lg+` | `LeftPanel` (Queue and History tabs) |
| `main` | `flex: 1; minWidth: 0` | the players strip, then `TicketView` |
| `floating` | `position: fixed` at the bottom of the window | the `Hand`, in every phase |

Below `lg` the row is a column (gap 16px) in the order Queue, Ticket (strip first, then the ticket), and there is no handle.

Resizable tickets pane (`lg+`). Between the panes sits `ResizeHandle`: a 9px hit area with a 1px `divider` line and a small grip, and the line turns `primary.main` and 2px wide on hover, focus-visible and while dragging. The default queue width is one third of the row, the clamp is 260px to the smaller of half the row and the row minus `TICKET_MIN_WIDTH`, and it is re-clamped on window resize (a `ResizeObserver` on the row). `TICKET_MIN_WIDTH` (873px) keeps the players strip one row (user ruling, 11/06/2026): the strip does not wrap at `lg`, so with the queue dragged wide at a 1200px window the Ticket column was narrower than the revealed controls, which overflowed the strip and left the pills no room. It is `CONTROLS_RESERVED_WIDTH` (680) plus the strip's 16px gap (`STRIP_COLUMN_GAP`), a 160px pill area (`MIN_PILL_AREA`, two compact pills with some left for a classic scrollbar) and the handle's 9px and two 4px margins (`RESIZE_HANDLE_WIDTH`, `RESIZE_HANDLE_MARGIN`, shared with `ResizeHandle` through `layoutConstants.ts`). The clamp is computed on every render, so it applies to the drag (it is the handle's `max`) and to a stored width restored on load alike. On a row too narrow for both minimums (under 1133px, a window under about 1181px, so only below `lg`, where the width is not used) the queue's 260px minimum wins. At a 1200px window the queue can then grow only from 260 to 279px. Dragging uses pointer events with `setPointerCapture` (mouse, touch, pen) and sets `user-select: none` on the body. Double-click resets to the default. The handle is `role="separator"` with `aria-orientation="vertical"`, `aria-label="Resize tickets pane"` and percentage `aria-valuenow/min/max`; ArrowLeft and ArrowRight move 16px, Home and End jump to the min and max. The width is stored in px in `localStorage` under `pp.layout.queueWidth` through `readJson` and `writeJson` in `storage.ts`, written on drag end and on key changes (not on every pointermove) and removed on reset. Invalid stored values are ignored.

Floating group. A `Box` wrapping the `floating` slot, which holds only the hand (11/06/2026: the results moved into the strip), `position: fixed`, `bottom: 0`, `transform: translateX(-50%)`, `zIndex: theme.zIndex.appBar` (above pane content, below menus, dialogs and the snackbar) and `width: max-content`. The width matters: a fixed box with `left` and `translateX(-50%)` shrink-to-fits into only the space to the right of `left` (a group centered far right once wrapped the deck onto two rows), and close to the right edge a box narrower than the hand would throw off both the centering and the clamp. With the pill gone, the group no longer has a flex arrangement, a gap, a `maxWidth` cap or `pointer-events: none` with its children `auto`: the box is exactly the hand's root, so it has no empty parts that clicks must pass through. Below `lg`, `left` is 50% of the window. At `lg` and up it is the CSS variable `--floating-center`, so the group is centered on the Ticket column, not the window, and moves with the resize handle. Layout writes two variables on the Container from a layout effect, straight to `style` so a resize does not re-render the tree, using a `ResizeObserver` on the group and on the Ticket column plus a window `resize` listener: `--floating-height` (the group's rendered height, rounded) and `--floating-center`. The center is the Ticket column's horizontal center, clamped so the whole group stays `FLOATING_EDGE` (16px) inside the window: `min = groupWidth / 2 + 16`, `max = window.innerWidth - groupWidth / 2 - 16`. Centered on a right-hand column at 1300px, the revealed pill ran past the right edge before the clamp (added in review); with the 256px hand alone the clamp is a safeguard, and it stays. A group wider than the window minus both edges has no center that keeps it inside, so it uses the middle of the window. The same effect writes the group's height plus the fade (`FADE_HEIGHT`, 24px) to `document.documentElement.style.scrollPaddingBottom`, for focus scrolling below `lg` (see Pane scrolling), and clears it on unmount. It also writes the Ticket column's left edge and width as `--ticket-left` and `--ticket-width` (rounded px), for the fade band.

Fade band (user ruling, 11/06/2026). With nothing behind them, the hand and the pill (since moved into the strip) floated over the ticket text, which ran right up to them and looked cluttered. A second fixed `Box`, `aria-hidden`, sits just before the floating group in the DOM with the same `zIndex: theme.zIndex.appBar`, so it paints above the panes and under the group, and under menus, dialogs and the snackbar. It is `bottom: 0`, `pointer-events: none` (it never takes a click) and `calc(var(--floating-height, 0px) + 24px)` tall (`FADE_HEIGHT` = 24; the expression is `BAND_HEIGHT` in `Layout.tsx`, shared with the panes' spacer, the page's bottom padding below `lg` and the panes' focus scroll padding). Its background is `linear-gradient(to bottom, <background.paper at alpha 0>, <background.paper> 24px)`: text fades out over the top 24px and the band is solid behind the group, so no text runs behind the cards. At `lg` and up it spans the Ticket column (`left: var(--ticket-left)`, `width: var(--ticket-width)`); below `lg` it spans the window (`left: 0`, `width: 100%`). The group is the 48px hand in every phase, so the band is 72px tall and no longer jumps at the reveal.

Pane scrolling (lg and up). Each pane's content sits in a `Box component="section"` with an `aria-label` ("Tickets", "Ticket"). At `lg` and up it has `height: PANE_HEIGHT`, `overflowY: "auto"` and is a flex column. The constants at the top of `Layout.tsx`:

- `HEADER_HEIGHT = 48`, imported from `layoutConstants.ts` (the same constant `Header` uses for its own height).
- `PAGE_TOP_PADDING = 16` (Container `pt`; no bottom padding at lg and up).
- `PANE_HEIGHT = calc(100vh - 48px - 16px)`: the header and the top padding only. The floating group does not take space in the page, so the panes run to the bottom of the window and the group floats over their bottom edge.
- Full-height cards (user ruling, 11/06/2026). A pane that stopped where its content ended left a blank page under a short queue or ticket, which the old bottom bar used to hide. So the pane's height is fixed (it was a `maxHeight`) and its last child, the `Paper` that draws the card's edge (`LeftPanel`'s, or `TicketView`'s under the players strip), has `flex: 1 0 auto`: it grows to the bottom of the window and never shrinks, so a long ticket still scrolls. Below `lg` nothing changes.
- The room for the floating group is a spacer at the end of that `Paper` (`& > :last-child::after`, a block `calc(var(--floating-height, 0px) + 24px)` tall), so the last lines scroll clear of the group and the fade band: the hand's height in every phase. It replaces the pane's `paddingBottom`, which ended the `Paper` above the group and left the blank strip back under it. Below `lg` the panes stack and a spacer in both would leave a gap between them, so the Container pads its end instead (`pb: calc(24px + var(--floating-height, 0px))`, 24px rather than 16px so the page's end also clears the fade).
- The open arc may cover the bottom of both panes while you pick. That is the trade the user accepted in the playtest.
- Focus scroll padding (added in review, WCAG 2.4.11). Scrolling a focused element into view stops at the pane's edge, so a focused link could land under the floating group or, in the Ticket pane, under the sticky players strip. The bottom padding is the whole fade band, not only the group, because an element stopped inside the band's top 24px came out washed out (review, 11/06/2026). At `lg` and up each pane has `scrollPaddingBottom: calc(var(--floating-height, 0px) + 24px)` (`BAND_HEIGHT`), and `Pane` takes a `stickyTop` prop that becomes `scrollPaddingTop`: the Ticket pane passes `STRIP_HEIGHT` (52, from `layoutConstants.ts`, the same constant `Players` uses for the strip's height). Below `lg` the page scrolls instead, and `html` cannot read the Container's variable, so Layout writes the group's height plus 24px to `html`'s `scroll-padding-bottom` directly. The strip is not sticky below `lg`, so there is no top padding there.

The Container is a flex column and the pane row has `flexGrow: 1`. With the header above it, the panes are exactly the rest of one viewport at lg and up and only the two panes scroll; the page itself has no vertical scrollbar. Below `lg` panes grow naturally and the page scrolls.

### components/HtmlBody.tsx and the safety rule

Props: `{ html: string }`. A `Box` with `dangerouslySetInnerHTML={{ __html: html }}` and an `sx` that styles `& p, & ul, & ol, & pre, & table, & blockquote` (bottom margin), `& ul, & ol` (left padding), headings (body-sized, bold), `& a`, `& code` (monospace, subtle background), `& pre` (`overflowX: "auto"` so wide code scrolls sideways), `& table` (`display: "block"`, `overflowX: "auto"`, `maxWidth: "100%"`, collapsed borders) and `& blockquote` (left border, muted). The root has `overflowWrap: "anywhere"` so long words and URLs wrap. Description and comments share it, so the rule lives in one file.

`descriptionHtml` and each comment's `bodyHtml` are sanitized on the server before they are sent: allowlisted tags only, no scripts or styles, images replaced by links, links already carrying `target` and `rel`. The client renders them with `dangerouslySetInnerHTML`, and that is safe only because of the server sanitizer. Two rules follow. First, `HtmlBody` is the only place in the client allowed to use `dangerouslySetInnerHTML`, and it carries `// biome-ignore lint/security/noDangerouslySetInnerHtml: server-sanitized HTML only; see spec 03 section 2`. Second, no other HTML source may be rendered this way: not Jira summaries, labels, usernames, queue items, search results or error messages. Those stay plain React text, which React escapes. The client does no sanitizing of its own, so a bug in the server sanitizer is a client XSS bug; do not add a client-side sanitizer dependency to paper over it.

### components/Players.tsx

Props: `{ players: PlayerView[]; phase: Phase; meId: number | null; disabled: boolean; results: ReactNode; onReveal: () => void; onReset: (opts: { clearTicket: boolean }) => void }`. `results` is App's `RoundResults` element, passed through to `RoundControls`. A 1px `divider` bottom border. After the reveal that line holds the results and Reset, and `RoundControls` wraps them further at a phone's width. After reveal, when numeric votes differ, the highest and lowest render in amber (outlier, always with the value as text, `findOutliers`). The viewer gets a ring on the avatar and a bold name; offline players are faded (opacity 0.35), with no card while voting; after reveal an offline player who voted keeps a face-up card (still faded) and counts toward the outliers, because the stats include that vote. The avatar carries the full username as its accessible name (and `title`), each card has an `aria-label` such as "Ana voted 5, highest", and the list is a `ul` labeled "Participants".

Compact mode (kept from decision 48). When the pills do not fit, every pill hides its name at once and gets `title={username}` (the card's `aria-label` still carries the name), so the strip stays uniform. The fit is measured, not a player count. A second, hidden copy of the pills with names always shown (a `ul` with `height: 0` and `width: max-content`) is compared with the room left of the controls: at `lg`, `row.clientWidth - Math.max(controlsWidth, CONTROLS_RESERVED_WIDTH) - STRIP_COLUMN_GAP`; below `lg`, the whole row width, because the controls wrap onto their own line. The controls width is read with `getBoundingClientRect().width`, not `offsetWidth`, because a fractional width rounded down could let the names through by a fraction of a pixel and clip the last pill. The hidden copy sits inside an absolutely positioned box with `inset: 0`, `overflow: hidden`, `pointer-events: none`, `aria-hidden` and `visibility: hidden`, so a copy wider than the window (12 or more players) never widens the page, while the inner list's `scrollWidth` still reports the full width. Measuring the hidden copy, never the visible list, keeps dropping the names from flipping the decision back, which would loop. One `ResizeObserver` watches the strip, the controls cell and the hidden copy, so a reveal, a join or a resize re-checks. The effect is a layout effect, so the first paint is already in the right mode, and it depends on `isLg` from `useMediaQuery` with `noSsr: true` (there is no server rendering, and the default first render of `false` would run the check once with the stacked layout's rule at `lg`).

`CONTROLS_RESERVED_WIDTH = 680`. The controls are always counted at least this wide, whatever the phase, so compact mode does not depend on the phase: the voting controls ("N of M voted", Reveal, Reset) and the revealed ones (the results, then Reset) differ in width, and measuring only the current one would let names show in one phase and drop at the reveal (the user's ruling in decision 48, kept, and the user's "stable always" of 11/06/2026). Since the results moved into the strip (11/06/2026) the revealed layout is the wider, so it sets the reserve. Measured in Chrome (11/06/2026): the revealed controls were 591px with a one-bar chart and "Consensus"; the widest case (a three-bar chart, "Spread 13–21", Points "0.5") is about 640px, so 680 keeps about 40px to spare. The user chose to keep the one-row strip with this reserve. It lives in `layoutConstants.ts`, because Layout's queue clamp uses it too. The cost: with many players the names switch to initials sooner than with the old 260px voting reserve, in both phases, because the reserve holds while voting too. It is also the CSS `minWidth` of the controls cell at `lg`, so a wider real layout (a chart with many bars) counts at its real width. The old 260 was measured while voting ("0 of 1 voted" 90px, Reveal 68px, Reset 64px and two 8px gaps, 238px) and replaced `SUMMARY_RESERVED_WIDTH` (370).

### components/Hand.tsx

Props: `{ deck: readonly string[]; selected: string | null; disabled: boolean; disabledHint: string; onSelect: (card: string) => void; onClear: () => void }`. The vote cards, replacing `Deck` (decision 51): a small fan peeking up from the bottom edge of the window, dealt into an arc on hover or keyboard focus. There is no bar behind it; Layout's fade band (see Layout) keeps text from running behind it. The playtest mock (`docs/spec/mocks/hand-of-cards-playtest.html`) is the reference for the feel, and the values below are the ones the user approved.

Geometry lives in `client/src/lib/handLayout.ts`, which has no imports so it can be checked with a throwaway `node -e` and no client build. Cards are 46×64px (`CARD_WIDTH`, `CARD_HEIGHT`). At rest each step from the middle card is 19px sideways, 4° of tilt and a drop of 0.4px per step squared (`REST`). The step was 11px; it was raised to 19 on 11/06/2026 so the corner index shows (see below). With it the gap between neighboring top-left corners, after the tilt, is 20.6 to 21.6px, and across the value's ink the strip each card leaves uncovered by the next is at least 20.3px. The widest value, "0.5" in Lato Bold at 11px, inks 14.8px from a 4px inset and clears the next card by 1.7px. 14 left 15.3px and cut "0.5", "13" and "21"; 18 clears "0.5" by 0.7px. `restHalfWidth(cards)` is half the resting fan's width: the end card's `x` plus its tilted half-width (`23·cos θ + 32·sin θ`), reached at its outer top corner, which is inside the peek (about 127.6px for 11 cards). Open (the Medium spread) it is 52px sideways, 5° and 2.2px per step squared (`OPEN`). `cardPose(offset, open, step)` returns `{ x, y, rotate }`, with `offset` the card's index minus the middle index; the open drop is scaled by `step / 52`, so a narrowed arc keeps its shape instead of turning into a deep U. `openLift(cards, step)` is the end cards' drop plus 20px, so the outer cards (0 and ☕) land just above the bottom edge and nothing is cut off. `fitStep(available, cards)` is `min(52, (available - 46) / (cards - 1))`.

The root is a `role="toolbar"` `Box`, 48px tall (`ROOT_HEIGHT` = the 30px peek plus the 18px the selected card is raised, so the panes' bottom spacer clears the whole peek) and `2 * ceil(restHalfWidth(deck.length))` wide (256px for 11 cards). It was a fixed 120px; with the 19px step the end cards reached 128px from the center, past the 120px root and the 20px gap, under the pill's left end at `lg`, so it was sized to the fan. Re-checked when the pill left (11/06/2026): nothing sits beside the hand now, but the width is still needed. Layout's clamp keeps the group's box 16px inside the window, so a narrower root would let the end cards run past the edge, and the closed hover zone (the root plus 20px a side) would stop short of them. The cards are absolutely positioned `button`s, one per deck card. Each takes its pose from CSS variables set inline (`--pose`, `--hover-pose`, `--delay`), because an inline `transform` would beat the `:hover` rule. At rest about 30px of the fan shows above the bottom edge. Closed, each value is a corner index, as on a fanned hand of real cards: 11px bold, `lineHeight: 1`, at the card's top-left with 4px of padding (`placeItems: "start"`), because each card covers the next one's middle and only a strip at its left edge shows (11/06/2026; the top-center value of the mock was covered on every card but your raised one and ☕). Your current vote is raised 18px, filled `primary.main` and keeps its corner index. Open, the cards deal up with a 10ms stagger per step from the middle, the values center at 18px, and the selected card is raised 8px. A hovered or focused card lifts 12px more, is drawn on top and gets a 2px `primary.main` outline. Your vote has no `zIndex` of its own, open or closed (11/06/2026): every card keeps deck-order stacking. Each corner index is in the strip at a card's left edge, which the next card never covers, so the raised vote's index shows without being put on top. Put on top (the old `zIndex: 2` in the closed peek) it covered the next card's index instead, and open it covered the next card's value when the arc narrowed, which the value padding relies on not happening (PR #9 review). The hover lift is under `@media (hover: hover)` only (added in review), because touch browsers keep `:hover` on the last tapped element, which left a card stuck lifted; focus-visible lifts it at any width. The root no longer sets `zIndex`: its `zIndex: 1` (added in review) only kept the faded pill, later in the DOM, from veiling the open arc's right-end cards, and the pill is gone. A hint under the open arc reads "← → to move · Enter to vote · Esc to close". Under `prefers-reduced-motion: reduce` every transition is `none`, so the arc opens and closes with no movement or stagger.

Hover zone. An invisible `::before` on the root grows with the arc (CSS variables `--zone-side` and `--zone-height`, from `step` and `openLift`), so moving the mouse from the peek up to an end card (0 or ☕) never leaves the zone and never closes the arc. The side margin beyond the end cards is 130px at most, clamped to the room measured for the arc (half the available width plus 16px), and never less than half a card, so the zone does not reach past the window edge (PR #9 review). Closed, it extends 20px beyond the root on each side and is as tall as the root.

Open and close rules. A mouse entering the hand opens it unless a pick or Esc suppressed it. A mouse moving over it does the same (added in review): a mouse resting on the disabled peek when a round starts never enters again, so the first move opens it. The suppression lasts until the pointer leaves, so moving after a pick cannot reopen it. A pick (click, Enter or Space) votes, or takes the vote back when it is your current card (the same toggle as the server), and closes the hand right away, even with the mouse still over it (D4). It stays closed until the mouse leaves and returns or the keyboard reopens it (`suppressedRef`). A mouse pick also blurs the card, because focus on a card would reopen the arc; a keyboard pick keeps focus on the card. Focus from the keyboard (`:focus-visible`) reopens even after a pick; focus from a click does not, or clicking right after a pick would undo D4. Focus leaving the toolbar (Tab out) closes it. A mouse leaving closes it unless focus is inside, so a keyboard user's arc stays open when the pointer passes over it. Going `disabled` closes it.

Keyboard (D7). One tab stop by roving `tabIndex`: the card with focus, else your vote, else the middle card (5). Open: ← and → move focus between cards (clamped at the ends, no wrap), Enter or Space votes, Esc closes and suppresses. Closed: Enter, Space, ← and → only reopen the arc and never vote, so a second Enter after a keyboard vote cannot take the vote back. Holding Enter or Space does not repeat (added in review): a held key picked, reopened and picked again, which withdrew the vote; `onKeyDown` ignores `e.repeat` for those two keys. Space's `keyup` is prevented because a button clicks itself on it and `onKeyDown` already handled it, and a click with `detail === 0` (assistive technology, no pointer) always picks, open or closed (changed in review: on a closed hand it used to only reopen, so a screen reader's activation seemed to do nothing). That keeps the second-Enter rule, because Enter and Space never produce that click: their default is cancelled on `keydown` and `keyup`.

Touch. There is no hover, so a tap on the closed peek opens the arc (the pointer type and whether it was open are recorded on `pointerdown`), a tap on a card while open votes and closes it, and a tap anywhere but a card closes it. For a mouse the hover zone counts as part of the hand. These rulings were not tested by the user (decision 51).

Arc width fitting (added in review). The open arc is centered on the hand, and at `lg` the hand is centered on the Ticket column (clamped inside the window), not on the window, so the room is `2 * min(center, window.innerWidth - center) - 32`, with `center` taken from the root's own bounding box (never the cards, so the open transforms cannot feed back). `step` is state: `fitStep(available, deck.length)`, measured again, before paint, when the arc opens, and on a window resize (the measure waits one animation frame so Layout can re-center the group first). It used to observe the floating row too, because a reveal added the pill and moved the hand; with the hand alone in the group nothing else moves it while the arc is open (a drag of the Ticket column happens with the arc closed, and opening measures again). The 16px on each side is the spec's narrow-screen ruling. When the step narrows, each card's right padding grows by the part the next card covers, so the value stays in the visible part.

States. In `idle`, or when disconnected, App passes `disabled`: its buttons are disabled and the arc does not open. The hand stays steady (user ruling, 11/06/2026): there is no opacity, because the old 0.5 showed light gray outlines that read as a rendering glitch. ### usePointsPick.ts

`client/src/usePointsPick.ts`. `usePointsPick({ round, ticketKey, stats, deck }): { points: string; setManualPoints: (points: string) => void }`. The points logic that used to live in `ActionBar`, moved out so `RoundResults` stays a view. It has no `phase` parameter: only `RoundResults` calls it, and it is mounted only after the reveal. One thing changed with the move: `ActionBar` stayed mounted, so a stale pick was dropped when the round ended. `RoundResults` unmounts on Reset and Next, so a stale pick (in `sessionStorage`) is now dropped at the next reveal instead, where it fails the ticket and round check. `suggestPoints` (`lib/estimate.ts`) is unchanged: the most common numeric vote, ties to the higher card.

- The value is local state initialised to `""`. An effect re-runs `setPoints(suggestion ?? "")`, where `suggestion = suggestPoints(stats, deck)` is computed in the hook body, on mount (each reveal) and when `ticketKey`, `round` or `suggestion` changes, so a new reveal or ticket never keeps a stale pick. It does not depend on `stats` itself (a new object every snapshot); `suggestion` is a string, so a vote change after the reveal re-suggests only when the most common vote actually changes. It carries this comment above the effect: `// biome-ignore lint/correctness/useExhaustiveDependencies: deck is stable; stats is omitted (a new object every snapshot), but suggestion is in the list so a vote change after the reveal re-suggests, and a manual pick (in memory, or stored for a refresh) still wins`.
- A manual pick sticks. `setManualPoints` sets the value and stores the pick in a `useRef<{ ticketKey: string; round: number; points: string } | null>` and in `sessionStorage`, because `writeJson` ignores failures: with storage blocked or full the stored copy is missing, and without the ref the next changed suggestion would silently replace the pick (PR review, 11/05/2026). The effect's order of preference for this ticket and round is the in-memory pick, then the stored pick, then the suggestion. A pick for another ticket or round clears the ref.
- A manual pick survives a refresh (kept from before the redesign, as spec section 3 item 4 requires). It is written to `sessionStorage` key `pp.points.pick` (per tab, so two tabs never overwrite each other) as `{ ticketKey, round, points }`. When the effect runs, a stored entry whose ticket key and round match the snapshot and whose points are a numeric deck card, is used instead of the suggestion (and copied into the ref). Any other stored entry is stale and is removed, so a new reveal or ticket still never keeps an old pick. The suggestion itself is not stored. With no ticket key nothing is stored.

### components/NoticeSnackbar.tsx

Props: `{ notice: { id: number; message: string; severity: "error" | "success" } | null }`. One shared toast for server errors, the local "Not connected" notice and Jira save results, so two toasts never stack. Holds its own `open` state. An effect keyed on the `notice` object sets `open` to `notice !== null`. Every event is a new object, so the same text arriving twice reopens the snackbar. It is not keyed on `notice.id`: the server's counter restarts at 1 after a server restart while the component survives the reconnect, so an id can repeat. MUI: `Snackbar open autoHideDuration={6000} anchorOrigin={{ vertical: "top", horizontal: "center" }}` whose `onClose(_, reason)` ignores `"clickaway"` and otherwise closes, containing `Alert severity={notice?.severity} variant="filled" onClose={close}` that shows `notice?.message`. Because it reads the prop, the last notice stays rendered during the exit transition and the severity does not flash to a default.

In MUI 9, `Stack` system props such as `flexWrap`, `alignItems`, `justifyContent` are no longer accepted as top-level props; they must go inside `sx`. The reference code already does this (`sx={{ flexWrap: "wrap" }}`, `sx={{ alignItems: "center" }}`). `direction`, `spacing` and `useFlexGap` stay as props. Follow the same rule in `App.tsx`.

## 3. useGameSocket hook (client/src/useGameSocket.ts)

Signature:

```ts
export function useGameSocket(): {
  snapshot: Snapshot | null;
  me: { userId: number; username: string } | null;
  connected: boolean;
  send: (cmd: ClientCommand) => boolean;
  error: { id: number; message: string } | null;
  disconnectedReason: "unauthenticated" | "bad_origin" | null;
  search: (query: string) => void;
  searchResults: { query: string; items: QueueItem[]; error: string | null; pending: boolean } | null;
}
```

The first four members are the contract from the plan. `error` and `disconnectedReason` are additions required by section 4; keep them in the same returned object. Types come from `../../shared/protocol.ts` via `import type` (including `QueueItem` for the search results). The hook does not expose `deck`; `App` imports `DECK` from `../../shared/deck.ts` instead (the server sends the same constant in `hello`, and the hook may ignore it).

State: `snapshot`, `me`, `connected`, `error`, `disconnectedReason` are `useState`. A `socketRef` holds the current `WebSocket | null`. Everything else (attempt counter, timer, cancelled flag) lives inside the effect closure.

URL: `${location.protocol === "https:" ? "wss:" : "ws:"}//${location.host}/ws`. If `new URLSearchParams(location.search).get("devUser")` is non-empty, append `?devUser=${encodeURIComponent(value)}`. Always forward it when present; the server decides whether to honor it (only in dev with `ALLOW_DEV_USER=1`). Never hardcode a port.

Connection lifecycle, implemented in one `useEffect(..., [])`:

1. `let cancelled = false; let attempt = 0; let timer: number | undefined;` and a `connect()` function that creates `new WebSocket(url)`, stores it in `socketRef.current`, and attaches handlers.
2. `onmessage`: `JSON.parse(event.data)` inside try/catch (ignore malformed frames). Switch on `type`:
   - `hello`: `setMe(msg.me)`, `setConnected(true)`, `attempt = 0`. Connected means "hello received", not merely "socket open", so controls stay disabled until the server has identified the user.
   - `state`: `setSnapshot(msg.snapshot)`.
   - `error`: `setError({ id: msg.id, message: `${msg.message} (${msg.reason})` })`. The reason is in the text so users can report it. Each call creates a new object, which is what reopens the snackbar for a repeated error (the id is the server's counter and can repeat after a server restart).
   - `searchResults`: keep it only if `msg.query` equals the latest query sent (a ref); otherwise drop it as stale. If kept, `setSearchResults({ query: msg.query, items: msg.items, error: msg.error, pending: false })`.
   - Unknown types are ignored.
3. `onclose(event)`: `socketRef.current = null`; `setConnected(false)`; if `cancelled` return. If `event.code === 4401` set `disconnectedReason` to `"unauthenticated"` and return; if `event.code === 1008` set `"bad_origin"` and return (both terminal: no retry, no timer). Otherwise schedule a retry: `const delay = Math.min(10_000, 500 * 2 ** attempt) * (0.5 + Math.random() / 2); attempt += 1; timer = window.setTimeout(connect, delay)`.
4. `onerror`: do nothing; browsers always follow it with `close`.
5. The last `snapshot` and `me` are never cleared on close, so the page keeps showing the last known state (disabled, with the "Reconnecting…" status) while the socket retries. A fresh `state` arrives right after the next `hello`.
6. Cleanup: set `cancelled = true`, `window.clearTimeout(timer)`, then take the current socket, null out its `onopen/onmessage/onclose/onerror` handlers, and `close()` it. Nulling handlers first prevents a stale socket from calling setState or scheduling a retry after unmount.

StrictMode safety: in development React mounts, unmounts and re-mounts the effect. The cleanup above fully disposes the first socket (browsers may log "closed before the connection is established"; that is acceptable). Because each mount has its own closure-scoped `cancelled`, `attempt` and `timer`, the two mounts cannot interfere. Do not keep these in module scope.

Optional but recommended: inside the same effect add listeners for `window` `online` and `document` `visibilitychange` (when `document.visibilityState === "visible"`). If not cancelled, no terminal reason set, and there is no socket currently OPEN or CONNECTING, clear any pending timer, set `attempt = 0` and call `connect()` immediately. Remove both listeners in cleanup. This helps laptops that sleep and iframes in background tabs.

Search (`search(query)`): `useCallback` with an empty dependency list. It trims the query. Under 2 characters it cancels any pending debounce timer, clears `latestQuery` and sets `searchResults` to null, and sends nothing. Otherwise it records the trimmed query in `latestQueryRef`, restarts a 400 ms debounce timer, and when the timer fires it calls `sendSearch(query)`, which calls `send({ type: "searchTickets", query })` and, if that returned true, sets `searchResults` to `{ query, items: [], error: null, pending: true }`. The hook also watches `snapshot.queueSettings.projectKey`: when it changes while a query is active, it cancels the debounce and calls `sendSearch(latestQuery)` at once (or sets `searchResults` to null if the socket is down), so another player's project change never leaves the old project's results on screen. The server drops the superseded search, so the old project's result normally never arrives. Server `searchResults` messages are delivered only to the requester. The debounce timer is cleared on unmount, and `searchResults` is left as is on socket close (it is cleared the next time the user types).

`send(cmd)`: wrapped in `useCallback` with an empty dependency list so its identity is stable. It reads `socketRef.current`; if that is null or `readyState !== WebSocket.OPEN`, return `false` (drop the command; never queue). Otherwise `socket.send(JSON.stringify(cmd))` and return `true`.

## 4. App.tsx wiring

`App` calls `useGameSocket()` once and renders:

```
<>
  <Header connected={connected} meName={me?.username} controls={snapshot ? <QueueControls ... /> : undefined} actions={snapshot ? <>Auto-reveal and Auto-advance switches</> : undefined} />
  ...content...
  <NoticeSnackbar notice={notice} />
</>
```

Content states, in priority order:

1. If `disconnectedReason` is non-null: render only an `Alert severity="warning"` inside `<Container maxWidth="md" sx={{ py: 2 }}>`. For `"unauthenticated"` the text is "Open this app inside the hosting platform" followed by a sentence that sign-in is handled by the platform and this page cannot identify you on its own. For `"bad_origin"` the text is "This page was opened from an address the server does not accept" with a hint to contact the service owner. Do not render the board.
2. Else if `snapshot === null`: centered `CircularProgress` (inside a `Box` with `display: "flex"`, `justifyContent: "center"`, `py: 6`). Give it `aria-label="Loading"`.
3. Else the board: `<Layout left={...} main={...} floating={...} />`. Layout renders its own full-width Container, so App adds none around it. The full page order is Header, then Layout (two panes, then the floating group). Slots:

| Slot | Content |
|---|---|
| `left` | `<LeftPanel ... />` (wraps `QueuePanel` and `SessionHistory`) |
| `main` | a fragment: `<Players ... />` (the strip, with `results={<RoundResults ... />}`), then `<TicketView ticket={snapshot.ticket} />` |
| `floating` | `<Hand ... />` alone, in every phase |

Layout's floating wrapper holds only the hand (11/06/2026). Until then it laid out the hand and, after the reveal, the results pill: stacked below `lg` (the pill above the hand) and in a row from `lg`, with a 20px gap, pointer events off on the wrapper and back on for its children, and the pill faded to 0.15 opacity while the arc was open (`data-results`, `data-hand-open`). All of that went with the pill. `Hand` still carries `data-hand-open`, which its own CSS uses.

Derived values:

- `const disabled = !connected;`
- `const selected = snapshot.players.find((p) => p.userId === me?.userId)?.vote ?? null;` The server shows a player their own vote before reveal, so this works in `voting` too. It is a `Card | null`.
- `deck = DECK` (imported constant, passes as `readonly string[]`).

Props per component:

| Component | Props |
|---|---|
| Header | `connected`, `meName={me?.username}`, `controls` (QueueControls once a snapshot exists), `actions` (a fragment with the Auto-reveal and Auto-advance switches once a snapshot exists) |

The Hand is disabled in `idle` (no round to vote in) in addition to `!connected`: pass `disabled={disabled || snapshot.phase === "idle"}`, so votes can still change after the reveal (decision 45). This is the one place App adds a phase rule; the server would reject the vote anyway, but the cards should not invite it.

Command mapping, all through one helper `dispatch(cmd: ClientCommand)`:

| UI action | Command |
|---|---|
| Click an unselected card | `{ type: "vote", card: card as Card }` (the Hand's `onSelect` gives `string`; cast to `Card`, which is imported as a type from shared/protocol.ts) |
| Click the selected card (clear) | `{ type: "vote", card: selected }` because the server toggles; `selected` is non-null whenever `onClear` can fire, but guard with `if (selected)` |
| Reveal | `{ type: "reveal" }` |
| Toggle the Auto-advance switch (header) | `{ type: "setAutoAdvance", enabled }` (shows `snapshot.autoAdvance`) |
| Toggle the Auto-reveal switch (header) | `{ type: "setAutoReveal", enabled }` (the switch shows `snapshot.autoReveal`, so it follows the room, not local state) |
| Next (the results in the strip, phase `revealed`) | `{ type: "reset", clearTicket: true }`; returns to `idle` so the team picks the next ticket from the queue |
| Reset (the strip, phases `voting` and `revealed`) / Start round (phase `idle`) | `{ type: "reset" }`; keeps the ticket and starts a new round (from idle it starts a ticket-less round) |
| Queue row or search result click | `{ type: "loadTicket", key }` (the key comes from a server-provided item, so no trimming or case change is needed) |
| Change a queue setting | `{ type: "setQueueSettings", settings }` (only the changed fields) |
| Refresh queue | `{ type: "refreshQueue" }`, then always `{ type: "refreshProjects" }` (the server retries projects and boards, which can fail independently) |
| Type in the search box | Not through `dispatch`: App passes the hook's `search` as `onSearch`, which sends `{ type: "searchTickets", query }` after a 400 ms debounce |
| Save to Jira | `{ type: "saveEstimate", points }` |

Notice handling. `dispatch` calls `send(cmd)`; if it returns false, App shows a local notice "Not connected. Your action was not sent." The snackbar takes one `{ id, message, severity }`, so App keeps `const [notice, setNotice] = useState<{ id: number; message: string; severity: "error" | "success" } | null>(null)`. Server errors come from the hook's `error`; an effect (`[error]` dependency, with a `biome-ignore lint/correctness/useExhaustiveDependencies` comment if Biome flags it) copies the hook's error into `notice` (severity `"error"`) whenever it changes. A second effect watches `snapshot?.jiraSave` with a `useRef` holding the previous status; only the transition from `"saving"` to `"saved"` or `"error"` sets a notice (`Saved {points} pts by {by}` with severity `"success"`, or `jiraSave.message` with severity `"error"`). The ref exists so joining, reconnecting or refreshing while `jiraSave` is already `"saved"` or `"error"` shows nothing; every snapshot is a new object, so the object alone cannot tell a new result from a repeat. Both effects share the local id counter below. Local notices use a counter in a `useRef` that starts at -1 and decrements, so local ids are negative and never collide with the server's positive ids. Pass `notice` to `NoticeSnackbar`. Because controls are disabled when not connected, this notice is a safety net for the short window between a socket dying and the `close` event arriving.

`App` is a named export `App` in `App.tsx`; `main.tsx` imports it as `import { App } from "./App.tsx"`. No context providers, no reducers.

## 8. Accessibility and responsive rules

Accessibility checklist (all already satisfied by the reference components; do not regress them):

- The hand is `role="toolbar"` with `aria-label` "Your cards, current vote 5" ("Your cards, no vote" with none; "coffee break" is spoken for ☕). Its cards are native `button`s with `aria-pressed` and `aria-label` "Vote 5" ("Vote coffee break"). The hand itself is not a button, because a button inside a button is invalid HTML. It is one tab stop by roving `tabIndex` (the card with focus, else your vote, else the middle card).
- Each player's card has `role="img"` and an `aria-label` such as "Ana has voted", "Ana has not voted" or "Ana voted 5, highest"; the vote state is never conveyed by color alone (face-down versus dashed card, and outliers also carry text).
- The queue Selects have visible labels linked with `InputLabel` and `labelId`; the Refresh icon button has `aria-label="Refresh queue"`; the search `TextField` has a visible label ("Search tickets (key or text)"); the progress bars have accessible labels.
- Every interactive element is a native `button`, `input` or `a`, so Tab and Enter and Space work with no extra code. Do not add click handlers to non-interactive elements.
- Heading hierarchy: exactly one `h1` (in Header), at every width: below `lg` it is visually hidden, never `display: none`; the ticket summary is `h2`, and "Description" is `h3` under the summary. The Description, "Comments (n)" and "History" tab labels are tabs, not headings. Headings inside server HTML are styled at body size by `HtmlBody` (the sanitizer allowlist decides whether they appear at all).
- Each pane is a `section` with an `aria-label` ("Tickets", "Ticket"), and the players are a `ul` labeled "Participants", so screen reader users can jump between them.
- Comments, ticket history and session history are real lists (`List` renders `ul` with `li` items), so the count is announced. Each date is a `<time>` element with `dateTime`. History old and new values use `<del>` and `<ins>`, so the change is not conveyed by strike-through alone.
- Keyboard and the floating group: the group is last in DOM order, so Tab reaches the strip's buttons inside the Ticket pane, then the hand (one tab stop). The results' controls are in the strip, so Tab reaches them with the strip's other buttons, before the ticket. The group floats over the bottom of both panes, whose last card ends in a spacer (an `::after` on the pane's last child, the group's height plus the 24px fade) that lets the last line scroll clear of it and the fade band, and the browser scrolls a focused element into view inside its pane. Scroll padding keeps that element clear of the floating group and the fade band and, in the Ticket pane, of the sticky strip (WCAG 2.4.11; see Layout, Pane scrolling). The open arc may cover the bottom of both panes while you pick; that is the trade the user accepted (decision 51). Do not add `tabIndex` to the panes. The player avatars are not interactive and are not tab stops; the resize handle between the panes is a tab stop.
- The page has exactly one `h1` (in Header) at every width, visible from `lg` and visually hidden (clip pattern) below it. Ticket key links (in TicketView, the queue and the search results) are the only external links and use `rel="noopener noreferrer"`.
- The loading spinner has an accessible label. The snackbar's `Alert` has the implicit `role="alert"` so errors and save results are announced.
- Text contrast comes from the stock MUI theme; do not lower opacity on text other than the offline player rows. There are no exceptions now: the results pill used to fade to 0.15 while the arc was open, and the results moved into the strip (11/06/2026). The disabled hand no longer uses opacity; its values use `text.disabled` (11/06/2026).

Responsive rules:

- Breakpoints: laptop widths are the target. At `lg` (1200px) and up: two columns (queue 4 and main 8 of 12) with independent scrolling, the players strip sticky at the top of the Ticket pane, and the hand floating at the bottom of the window (section 2, Layout.tsx). Below `lg`: everything stacks full width in the order Queue, then the Ticket pane (the strip first, not sticky, then the ticket); the hand still floats at the bottom center and the page scrolls with room at its end. The strip wraps, so the results and Reset take their own row under the pills, and wrap further at a phone's width. No phone-specific work beyond "nothing breaks": no horizontal page scroll.
- Layout width: `Container maxWidth={false}` uses the whole page, with `px: { xs: 2, lg: 3 }` side gutters and no `maxWidth` cap.
- The floating group is only the hand: centered on the window below `lg`, and from `lg` centered on the Ticket column and clamped 16px inside the window (see Layout). The pill that stacked above it below `lg` moved into the strip (11/06/2026).
- The hand never wraps: its cards are absolutely positioned in a fixed 256×48px root (sized from the resting fan), and the open arc narrows its step to fit the room (see Hand). The results wrap below `lg` inside `RoundControls`' row.
- The header is a fixed 48px single row from `lg`. Below `lg` it is two rows (controls, then switches and status) and grows; the title is visually hidden there (still the one h1 for screen readers), and the queue selects shrink to `minWidth` 110 at `xs` and wrap so the header does not overflow on phones.
- No horizontal page scroll at 1000px or at 1440px. Verify by resizing the browser.
- Do not use fixed pixel widths on containers. `minWidth: 140` (110 at `xs`) on the three header selects, `minWidth: 96` on the points select, `maxWidth: 96` on pill names, the strip's `CONTROLS_RESERVED_WIDTH` (680, measured) and the hand's 46×64px cards in a 256×48px root are the only fixed widths. The fixed heights (header 48, strip 52) apply at lg and up only.

## 9. Acceptance checklist for the implementer

Run `npm run lint`, `npm run tsc:check` and `npm run build`; all must pass with no Biome warnings (the five `biome-ignore` comments are expected (`useExhaustiveDependencies` in `usePointsPick`, QueuePanel and TicketView, `noArrayIndexKey` in TicketHistory, and `noDangerouslySetInnerHtml` in HtmlBody) and must include their explanation text). Do not write tests. Then verify in a browser with `npm run dev` and `ALLOW_DEV_USER=1` set in the environment (or `.env`; never read or print `.env`):

1. Open `http://localhost:3838/?devUser=alice` in one browser profile and `http://localhost:3838/?devUser=bob` in another (separate profiles or one normal and one private window, so the identity does not collide). Each shows "You are alice" / "You are bob" and both appear in each other's list.

Change the project and confirm the board select reloads its options and the list changes on both pages.
